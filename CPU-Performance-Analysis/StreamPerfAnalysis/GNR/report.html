SNC3 interpretation

Sub-NUMA Clustering divides each socket into three NUMA locality domains. Each domain here contains 32 physical cores, their SMT siblings, and roughly 252 GiB of local memory.

  • Local-node distance: 10
  • Another SNC node in the same socket: 12
  • A node on the other socket: 21

A single-node STREAM run measures one SNC domain. A full-socket run must use all three nodes belonging to that socket and distribute memory pages across those nodes.

STREAM kernels and traffic model

STREAM uses double-precision elements (8 bytes each). Reported bandwidth counts useful algorithmic reads and writes.

Addc[i] = a[i] + b[i]116 B read + 8 B write = 24 BTwo read streams, one write stream, load ports and MLP
Triada[i] = b[i] + scalar × c[i]216 B read + 8 B write = 24 BTwo read streams, one write stream, vector multiply-add/FMA

Write allocation and non-temporal stores

With an ordinary write-back store, a destination cache line that is absent from cache normally triggers a Read For Ownership (RFO). The processor reads the 64-byte destination line, modifies it in cache, and later writes the dirty line back. For a full-line streaming overwrite, the initial destination read is unnecessary useful work.

Kernel pattern per destination cache lineUseful trafficPossible traffic with RFO
Copy/Scale64 B source read + 64 B destination write = 128 B64 B source read + 64 B destination RFO + 64 B writeback = 192 B
Add/Triad128 B source reads + 64 B destination write = 192 B128 B source reads + 64 B destination RFO + 64 B writeback = 256 B

Non-temporal stores use write-combining behavior and normally avoid bringing the destination line into the ordinary cache hierarchy, eliminating the RFO for aligned full-line streaming stores. They also reduce cache pollution. They are a processor hint rather than an absolute promise and can hurt when the written data will be reused soon.

On x86, generated non-temporal store instructions can be checked with objdump -d -M intel ./stream | grep -i movnt. Disassembly of both the original STREAM executable and the isolated-kernel executable showed ordinary temporal vmovupd stores and no movnt* instructions.

Despite the temporal stores, the isolated-kernel PCM measurements below do not show an additional destination-line read at DRAM. Ownership is still required in the cache-coherence protocol, but the observed memory-controller traffic is consistent with GNR avoiding the old-data DRAM fetch for these complete cache-line overwrite streams. This is an observed result, not an assumption based only on instruction type.

Intel PCM source build

The packaged PCM build dated 2024-01-25 rejected model 173 as unsupported. The current Intel PCM source build correctly identifies Intel Xeon 6972P as Granite Rapids.

sudo dnf install -y git cmake gcc gcc-c++ make libasan

git clone --recursive https://github.com/intel/pcm.git
cd pcm
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel "$(nproc)"

./build/bin/pcm-memory --version

The repository helper is scripts/build_intel_pcm.sh. It clones recursively, configures a Release build, builds in parallel, and records the exact Git revision.

PCM command: original four-kernel STREAM run

pcm-memory 0 -- \
numactl --physcpubind=0-31 --membind=0 \
env OMP_NUM_THREADS=32 OMP_PLACES=cores OMP_PROC_BIND=close \
./stream

The combined run reported 78.895 GB/s system reads, 53.894 GB/s system writes, and 132.788 GB/s total. Because it contains initialization and all four kernels, its aggregate read/write ratio cannot identify the behavior of an individual kernel.

Isolated STREAM-kernel experiment

A kernel-selectable benchmark, scripts/stream_single_kernel.c, was added so that PCM can measure Copy, Scale, Add, and Triad separately. Each run uses 200 iterations over 100,000,000 doubles per array (0.745 GiB/array), 32 physical cores from NUMA node 0, and memory allocated on node 0.

Build and instruction check

gcc -O3 -march=native -fopenmp \
stream_single_kernel.c -o stream_single_kernel

objdump -d -M intel ./stream_single_kernel | \
grep -E 'vmovnt|movnt'

The instruction check returned no non-temporal stores.

Run commands

PCM=/path/to/pcm/build/bin/pcm-memory

SNC channel validation

For all four isolated runs, significant node-0 traffic appears on memory channels 2, 3, 8, and 9. Traffic is balanced closely across those four channels; the remaining socket-0 channels show only background traffic. This validates that NUMA node 0 is one four-channel SNC3 domain with a theoretical ceiling of 204.8 GB/s.

Scaling interpretation

  • Bandwidth scales strongly through 16 physical cores.
  • Increasing from 8 to 16 cores adds 52.578 GB/s.
  • Increasing from 16 to 32 cores adds only 8.881 GB/s.
  • The declining bandwidth per core and weak gain after 16 cores show that the SNC memory subsystem is approaching saturation.
  • The remaining approximately 19% gap from theoretical peak is not explained by insufficient core concurrency at the 32-core point.
  • All active channels remain balanced, so a single poorly utilized channel is not the apparent cause.

Counter-based gap analysis: next step

The next experiment will use the exact events exposed by the installed GNR kernel and perf package. Candidate evidence includes IMC read/write queue occupancy, queue-full cycles, DRAM page hits/conflicts, refresh activity, read/write turnaround pressure, and core Top-Down Memory Bound metrics.

perf list | grep -Ei \
'cas_count|rpq|wpq|page.*hit|page.*miss|refresh|memory_bound|dram_bound'

for directory in /sys/bus/event_source/devices/uncore_imc_*; do
    echo "===== $(basename "$directory") ====="
    ls "$directory/events" 2>/dev/null
done

perf list | grep -Ei \
'tma_memory_bound|tma_backend_bound|memory_bound|topdown'

Once available event names are recorded, counters will be collected at the 8-, 16-, and 32-core points. A bandwidth plateau accompanied by sustained full queues would identify controller/DRAM saturation; continued scaling with low queue occupancy would instead indicate insufficient request generation.
