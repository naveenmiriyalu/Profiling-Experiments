Granite Rapids STREAM Performance Analysis

Status: one-SNC baseline complete. Follow-up socket and system scaling experiments are listed at the end.

Executive conclusions

  • One SNC3 domain contains 32 physical cores and four DDR5-6400 channels, giving a theoretical 204.8 GB/s peak.
  • Triad reaches 165.947 GB/s useful bandwidth, about 81.0% of that theoretical channel peak, and is effectively saturated by 16–24 cores.
  • Top-Down confirms the transition to a DRAM-bound workload: DRAM Bound rises from 54.4% at 8 cores to 85.9% at 32 cores while frequency remains stable.
  • Explicit subchannel CAS events agree with PCM; the generic GNR IMC aliases cover only part of the scheduler/subchannel traffic and must not be treated as totals.
  • At 8 cores, temporal stores generate one extra 160 GB RFO stream. AVX-512 non-temporal stores remove it and improve useful bandwidth by 23.8%.
  • At 16 cores, temporal stores already avoid nearly all of that RFO traffic, so explicit non-temporal stores provide no further speedup.

SNC3 interpretation

Sub-NUMA Clustering divides each socket into three NUMA locality domains. Each domain here contains 32 physical cores, their SMT siblings, and roughly 252 GiB of local memory.

  • Local-node distance: 10
  • Another SNC node in the same socket: 12
  • A node on the other socket: 21

A single-node STREAM run measures one SNC domain. A full-socket run must use all three nodes belonging to that socket and distribute memory pages across those nodes.

Write allocation and non-temporal stores

With an ordinary write-back store, a destination cache line that is absent from cache normally triggers a Read For Ownership (RFO). The processor reads the 64-byte destination line, modifies it in cache, and later writes the dirty line back. For a full-line streaming overwrite, the initial destination read is unnecessary useful work.

Kernel pattern per destination cache lineUseful trafficPossible traffic with RFO
Copy/Scale64 B source read + 64 B destination write = 128 B64 B source read + 64 B destination RFO + 64 B writeback = 192 B
Add/Triad128 B source reads + 64 B destination write = 192 B128 B source reads + 64 B destination RFO + 64 B writeback = 256 B

Non-temporal stores use write-combining behavior and normally avoid bringing the destination line into the ordinary cache hierarchy, eliminating the RFO for aligned full-line streaming stores. They also reduce cache pollution. They are a processor hint rather than an absolute promise and can hurt when the written data will be reused soon.

On x86, generated non-temporal store instructions can be checked with objdump -d -M intel ./stream | grep -i movnt. Disassembly of both the original STREAM executable and the isolated-kernel executable showed ordinary temporal vmovupd stores and no movnt* instructions.

Despite the temporal stores, the isolated-kernel PCM measurements below do not show an additional destination-line read at DRAM. Ownership is still required in the cache-coherence protocol, but the observed memory-controller traffic is consistent with GNR avoiding the old-data DRAM fetch for these complete cache-line overwrite streams. This is an observed result, not an assumption based only on instruction type.

Interpretation of the core counters

  • Constant work: retired instructions remain near 15.8 billion, confirming that the three runs execute comparable work.
  • No frequency explanation: average active frequency remains close to 3.1 GHz at every core count, so frequency throttling does not explain the bandwidth plateau.
  • Falling IPC: IPC drops from 0.14 to 0.05 as more cores share the same four memory channels. Additional cores spend more time waiting rather than retiring more instructions.
  • Backend dominance: Backend Bound is already above 97% at eight cores; frontend delivery and bad speculation are not material bottlenecks for this streaming loop.
  • Increasing DRAM pressure: DRAM Bound increases from 54.4% to 78.6% to 85.9%, while useful bandwidth begins to plateau. This links the scaling loss directly to off-core DRAM waiting.

Top-Down hierarchy

The percentages are nested classifications and must not be added:

Backend Bound
└── Memory Bound
    └── DRAM Bound

A core may be Memory Bound before the complete SNC memory subsystem is saturated. At eight cores, individual cores already wait frequently for memory, but adding more cores supplies additional concurrent requests and raises aggregate bandwidth. By 16–32 cores, extra concurrency mostly increases DRAM wait time rather than useful bandwidth.

The slots count is approximately six times the cycle count, consistent with six Top-Down pipeline slots being classified per cycle on this processor. Top-Down retiring slots are not the same quantity as retired instructions.

For a raw CAS count, transferred bytes are normally derived from the transfer size. However, perf reads the event's sysfs .scale and .unit files and prints these generic events directly in MiB. A value already labelled MiB must not be multiplied by 64 again:

Average bandwidth (MiB/s) = perf-reported MiB / perf elapsed seconds

Raw subchannel-specific events must be interpreted using their own event definitions and scale. GNR exposes two scheduler/subchannel families, sch0 and sch1, which must be validated and summed before claiming total DRAM traffic.

How to interpret RPQ counters and multiplexing

Why perf multiplexed the events

An uncore memory-controller PMU has a limited number of programmable hardware counters. The original command requested eight events at once: four RPQ insert events and four RPQ occupancy events. Because all eight could not remain scheduled simultaneously, Linux perf time-shared the available registers between event sets. The approximately (50%) value beside each result means that event was physically active for only about half of the measurement interval.

perf scales a multiplexed count approximately as:

reported count = raw observed count × enabled time / running time

This scaling assumes the event rate is reasonably stable while the event is not being counted. STREAM's steady state makes the scaled trend useful, but a non-multiplexed capture is preferable. Multiplexing may also perturb execution, and the multiplexed runs were slower than the clean sweep, especially at eight cores.

RPQ inserts

unc_m_rpq_inserts.* counts read requests inserted into the memory controller's Read Pending Queue for the selected scheduler and pseudo-channel. It measures request volume, not waiting time. The summed eight-core insert count closely matches the explicit read-CAS total, which provides a useful consistency check.

RPQ occupancy

unc_m_rpq_occupancy_* accumulates queue depth over controller ticks. If the queue contains 3, 5, and 4 entries on three successive ticks, the counter adds 3 + 5 + 4 = 12 entry-ticks. It is therefore the time-integral of queue depth, not maximum occupancy and not directly the average queue depth.

Normalizing occupancy using inserts

The ratio below estimates average queue-residence ticks per inserted request:

residence indicator = summed RPQ occupancy / summed RPQ inserts

This is the counter form of Little's Law, L = λW, rearranged as W = L / λ. A rising ratio means requests are spending more controller ticks resident in the pending queue. It should not be converted to nanoseconds until the precise event semantics and relevant uncore clock frequency are validated.

Why the automated measurement uses two passes

The rpq mode collects scheduler 0 and scheduler 1 separately, with four events per pass. This is intended to keep each event near 100% running time and avoid the original 50% multiplexing. The tradeoff is that the schedulers are measured in separate benchmark executions, so their elapsed time and useful bandwidth must be checked for run-to-run stability before their counts are combined.

The explicit AVX-512 variant was verified in the disassembly by the presence of vmovntpd. Both variants then ran the same 200-iteration, 100,000,000-element Triad workload with explicit subchannel CAS counters.

At eight cores, non-temporal stores remove 159.82 GB of read traffic while retaining the output write stream. This is almost exactly one 160 GB output-array stream: 100,000,000 elements × 8 bytes × 200 iterations. The result strongly identifies the extra temporal-store traffic as write allocation/read-for-ownership rather than IMC underfill. Removing that traffic reduces kernel time by 19.2% and raises useful bandwidth from 104.122 to 128.875 GB/s, a 23.8% improvement.

At sixteen cores, temporal Triad already avoids nearly all of that extra read stream. This supports the earlier observation that Granite Rapids can dynamically avoid unnecessary write-allocation traffic for sustained full-line streaming stores. Explicit non-temporal stores make that behavior deterministic, but useful bandwidth is 1.3% lower here (155.259 versus 157.255 GB/s), so it provides no performance benefit once temporal stores receive the same effective RFO avoidance.

*CAS-rate nuance: the CAS-derived rates use the complete perf stat wall interval, which includes startup and teardown, whereas the benchmark's useful bandwidth uses its internally timed kernel region. Traffic totals and read:write ratios are therefore the cleaner evidence for this comparison.
