GPU Architecture — Specifications and Concepts

Purpose: persistent architecture reference for the GPU performance study. Experimental reports (memory/MLP, GEMM, graphics, LLM kernels) should reference this document rather than repeatedly redefining foundational concepts.

Registers, shared memory and L1/TEX are SM-local resources. L2 is GPU-wide and partitioned. HBM is off-chip device memory. Shared memory is explicitly managed scratchpad storage rather than merely another transparent cache level.

Sector/coalescing reminder

32 FP32 lanes × 4 B = 128 useful B
128 B / 32-B sector = 4 sectors for an aligned contiguous warp access

The earlier H200 experiment validated exactly four sectors/request for contiguous FP32 global loads/stores.

3. Local, constant and texture-related memory concepts

CUDA local memory is a per-thread address space that may be serviced through the cache/global-memory hierarchy; register spills are a common source of local-memory traffic. CUDA constant memory is intended for small read-only/broadcast-friendly data. L1/TEX terminology reflects the unified L1/texture subsystem and GPU texture/surface heritage.

4. The on-chip interconnect: what sits between SM-side requests, L2 and memory partitions?

A GPU is not wired as “every SM directly talks to one monolithic L2 cache.” Requests from many SMs/GPCs must be routed to the appropriate distributed/partitioned cache and memory resources. A useful conceptual model is a high-bandwidth on-chip fabric/crossbar network:

       SMs / GPCs
      /   |   |   \
     v    v   v    v
 +---------------------+
 |   on-chip routing   |
 |  fabric / crossbar  |
 +---------------------+
   |      |      |      |
   v      v      v      v
 L2 P0  L2 P1  L2 P2  L2 Pn
   |      |      |      |
   v      v      v      v
 memory partitions/controllers
             |
             v
            HBM

The important architectural idea is many-to-many bandwidth: many SM-side clients can generate traffic concurrently, and addresses distribute traffic across partitioned downstream resources. The fabric must sustain enormous aggregate traffic so the compute array, L2 and HBM can operate in parallel.

Why “the interconnect inside a GPU is good” is reasonable—but incomplete

On-chip communication is engineered for much higher aggregate bandwidth and lower latency than off-chip communication. This is one reason thousands of execution lanes can feed a shared L2/HBM subsystem. But it does not mean the fabric is infinitely fast or contention-free. Address mapping, request distribution, L2 partitions, crossbar ports, queues, memory partitions and hot spots can all matter. A profiler may therefore expose different utilization/imbalance at SM/L1TEX, L2 and DRAM levels.

Our MLP4/MLP8 experiment illustrated this nicely: request distribution widened strongly across upstream L1TEX metric instances at MLP8, while L2 reductions stayed comparatively tight and DRAM min/max was essentially unchanged. That suggests downstream routing/partitioning smooths much of the upstream distribution; it does not prove a particular undocumented topology.

Hopper adds thread-block clusters: groups of blocks guaranteed to run concurrently on a group of SMs within a GPC. This exposes locality/cooperation beyond a single SM and is relevant to distributed shared memory and advanced Hopper kernels.

5. Do not confuse three different “interconnects”

InterconnectWhereExample purpose
On-chip GPU fabric/crossbarInside one GPU dieRoute SM/GPC traffic to L2/memory-side resources
NVLinkGPU↔GPU (and supported coherent/chip-to-chip systems)High-bandwidth peer GPU communication
PCIeGPU↔host/platform devicesHost/device and platform I/O

When discussing “internal GPU interconnect” in the memory-hierarchy context, the first row is usually what matters. NVLink is a different, external chip/device interconnect.

6. Hopper external interconnect reference

H100 introduced fourth-generation NVLink. NVIDIA documents 18 links at 50 GB/s bidirectional data rate per link, yielding 900 GB/s aggregate bidirectional NVLink bandwidth for H100. This is distinct from the internal SM↔L2↔memory fabric.

7. Asynchronous data movement

ordinary demand:
HBM -> L2 -> L1/TEX -> Registers -> Compute

shared-memory staging:
HBM -> L2 -> Shared -> Registers -> Compute

software pipeline:
future tile: HBM/L2 ----------> Shared B
current tile: Shared A -> Registers -> Compute

Hopper:
TMA tile movement -> Shared -> Tensor operand pipeline -> Tensor Cores

MLP increases independent outstanding memory operations. Software pipelining overlaps future data movement with current compute. TMA provides Hopper hardware support for bulk multidimensional tensor movement.

8. Reference specifications used in this study

For the H100/Hopper architectural reference, NVIDIA documents a full GH100 implementation with 8 GPCs, up to 144 SMs, 60 MB L2 and 12 512-bit memory controllers; shipping H100 configurations use subsets of the full implementation. H100 SXM5 is documented with 132 SMs, 50 MB L2, five HBM3 stacks and ten 512-bit memory controllers. H200 is also Hopper-family but has product-specific HBM capacity/bandwidth; experimental measurements should use the actual device under test rather than blindly substituting H100 board specifications.

9. Questions to investigate experimentally

- How does address mapping distribute traffic across L2/memory instances?
- Can a deliberately pathological mapping create partition camping?
- How much L2 bandwidth can one versus many GPCs/SMs generate?
- How do thread-block clusters and distributed shared memory change locality?
- At what point does L2/fabric pressure become visible before HBM saturation?
- How do TMA pipelines alter request generation and fabric traffic?
