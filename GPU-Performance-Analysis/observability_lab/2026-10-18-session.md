# GPU PMU and Tracing Lab — Session 01 (2026-10-18)

**Theme:** Counts are not traces. **Duration:** 60 minutes. **State:** source code and lab prepared, not run on the GPU host during this session.

## 60-minute lab

0–10 min: Recall prior H200 Triad results. 10–20 min: PMU events and sector counters. 20–30 min: Sampling versus timestamped tracing. 30–50 min: Capture Nsight Systems kernel activities and export JSONL. 50–60 min: Check event attribution, timestamps, overflow warnings, and document uncertainty.

### Measured carry-over (prior H200 experiment)

| Observation | Value |
|---|---:|
| Useful traffic | 1.2 GB |
| Unprofiled time | 0.349 ms |
| Useful bandwidth | 3436.27 GB/s |
| DRAM read / write (NCU) | 800.05 MB / 388.02 MB |
| L1TEX global-load sectors | 25,000,000 |
| L1TEX sectors per load request | 4 |
| No eligible warp (scheduler cycles) | 75.31% |
| Long-scoreboard contribution | 40.8 of 47.25 warp cycles per issued instruction |

Data types must remain distinct: NCU sector counts are aggregate hardware-derived metrics. Nsight Systems records timestamped API/kernel events. PC or CPU-IP sampling observes selected occurrences and can be statistically biased. A synthetic memory-request stream constructed from kernel source is **reconstructed simulator input**, not a hardware-observed memory trace.

### Three exercises (self-check answers at end)

1. Convert 25M 32-byte sectors to bytes and compute requests at 4 sectors/request.
2. Which answers launch-to-GPU scheduling delay: Nsight Systems activity trace or NCU DRAM byte metric?
3. At 1 kHz CPU IP sampling, how many sample intervals would a 0.349 ms GPU kernel span? Does observing no CPU sample imply GPU inactivity?

### Capture on H200 (or B200 when available)

From GPU-Performance-Analysis:

~~~bash
OUT="reports/observability/h200_triad_$(date -u +%Y%m%dT%H%M%SZ)"
bash observability_lab/collect_nsys_trace.sh "$OUT" ./triad
head -3 "$OUT/kernels.jsonl"
cat "$OUT/kernel-summary.txt"
~~~

Collector artifacts: manifest.txt; nvidia-smi.txt; original timeline.nsys-rep; timeline.sqlite; kernel-summary.txt; and kernels.jsonl. The JSONL includes GPU kernel start/end, stream and correlation IDs, but **not** warp or memory-transaction accesses. Time units are Nsight-export nanoseconds, not independently comparable raw GPU/CPU clocks. Keep original NCU reports and the unprofiled baseline separately.

### CPU contrast

Run `perf stat -e cycles,instructions,context-switches -- ./triad` to count CPU-side work; these are not SM instruction counters. Collect CPU IP samples with `perf record` on a longer CPU workload; short GPU launches may produce no samples.

### Data-quality checks

Preserve raw reports; capture device and driver, profiling versions, command, dataset size, git revision, and UTC time. Inspect buffer-drop warnings. Distinguish counter wrap/overflow from dropped activity records. NCU may replay kernels, perturbing in-application timings. CPU/GPU correlations should use profiler mappings/IDs; do not join independent runs by arbitrary timestamps. Review traces for sensitive identifiers before public uploads.
