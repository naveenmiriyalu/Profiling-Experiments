GPU Performance & Architecture Study

Living report for GPU microarchitecture experiments, hardware profiling, ISA analysis, trace-driven simulation, LLM prefill/decode, and graphics. Initial hardware target: NVIDIA H200; comparative target: AMD MI355X.

Part I — GPU Architecture Foundations

1. Thread → Block → Warp → Lane

A CUDA kernel is launched as a grid of blocks. Threads have a block-local threadIdx; a common 1-D global index is blockIdx.x * blockDim.x + threadIdx.x. NVIDIA groups 32 threads into a warp. The lane is the thread's position inside that warp.

2. Global Memory Access & Coalescing

For FP32, one lane requests 4 B. A full 32-lane warp performing a contiguous load therefore requests 128 useful bytes.

32 lanes × 4 B = 128 useful B

For our Hopper experiment, we begin with a 32-B sector mental model. Eight adjacent FP32 lane accesses fit in one sector.

Important: useful bytes, sector bytes, cache traffic and actual HBM traffic are distinct quantities. The experiment will test how the simple prediction maps onto real H200 behavior.

3. Alignment

An aligned contiguous 128-B warp load can occupy four 32-B sectors. Shifting the same access by 4 B can make it touch five sectors, giving 128/(5×32) = 80% simple useful-byte efficiency.

Experiment 1 — SM-driven stride read

out[i] = in[i * stride]

Initial configuration: FP32, 100,000,000 outputs, stride 1, 256 threads/block. Each output represents 4 B of useful input read plus 4 B of useful output write, or 0.8 GB application-level useful traffic for the full run.

Full CUDA source

#include <cuda_runtime.h>

#include <cstdio>
#include <cstdlib>

#define CUDA_CHECK(call)                                                   \
do {                                                                       \
    cudaError_t err = (call);                                              \
    if (err != cudaSuccess) {                                              \
        fprintf(stderr, "CUDA error at %s:%d: %s\n",                      \
                __FILE__, __LINE__, cudaGetErrorString(err));              \
        std::exit(EXIT_FAILURE);                                           \
    }                                                                      \
} while (0)

__global__ void stride_read(
    const float* __restrict__ in,
    float* __restrict__ out,
    size_t n,
    int stride)
{
    size_t i =
        static_cast<size_t>(blockIdx.x) * blockDim.x
        + threadIdx.x;

    if (i < n) {
        out[i] = in[i * stride];
    }
}

int main()
{
    const size_t N = 100'000'000;
    const int stride = 1;

    const size_t input_elements = N * stride;
    const size_t input_bytes = input_elements * sizeof(float);
    const size_t output_bytes = N * sizeof(float);

    printf("N               : %zu\n", N);
    printf("stride          : %d\n", stride);
    printf("input size      : %.2f MB\n", input_bytes / 1.0e6);
    printf("output size     : %.2f MB\n", output_bytes / 1.0e6);

    float* d_in = nullptr;
    float* d_out = nullptr;

    CUDA_CHECK(cudaMalloc(&d_in, input_bytes));
    CUDA_CHECK(cudaMalloc(&d_out, output_bytes));
    CUDA_CHECK(cudaMemset(d_in, 0, input_bytes));
    CUDA_CHECK(cudaMemset(d_out, 0, output_bytes));

    const int threads_per_block = 256;
    const size_t blocks =
        (N + threads_per_block - 1) / threads_per_block;

    printf("threads/block   : %d\n", threads_per_block);
    printf("blocks          : %zu\n", blocks);

    stride_read<<<blocks, threads_per_block>>>(d_in, d_out, N, stride);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaDeviceSynchronize());

    cudaEvent_t start;
    cudaEvent_t stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    CUDA_CHECK(cudaEventRecord(start));
    stride_read<<<blocks, threads_per_block>>>(d_in, d_out, N, stride);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaEventRecord(stop));
    CUDA_CHECK(cudaEventSynchronize(stop));

    float elapsed_ms = 0.0f;
    CUDA_CHECK(cudaEventElapsedTime(&elapsed_ms, start, stop));

    // Application-level useful traffic: one 4-B read + one 4-B write.
    // This is not necessarily equal to L1/L2/HBM traffic.
    const double useful_bytes =
        static_cast<double>(N) * 2.0 * sizeof(float);
    const double elapsed_seconds = elapsed_ms / 1000.0;
    const double useful_GBs =
        useful_bytes / elapsed_seconds / 1.0e9;

    printf("\n");
    printf("Kernel time     : %.3f ms\n", elapsed_ms);
    printf("Useful traffic  : %.3f GB\n", useful_bytes / 1.0e9);
    printf("Useful bandwidth: %.2f GB/s\n", useful_GBs);

    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));
    CUDA_CHECK(cudaFree(d_in));
    CUDA_CHECK(cudaFree(d_out));

    return 0;
}

PTX observations

The PTX preserves stride as a runtime kernel parameter. The input address is formed from i × stride × sizeof(float); the output remains contiguous. The actual data operation is a ld.global.nc.f32 followed by st.global.f32. PTX is a virtual ISA, so the final Hopper machine instructions must be checked in SASS.

SASS / nvdisasm workflow

nvcc -O3 -arch=sm_90 -lineinfo --cubin stride_read.cu -o stride_read.cubin
nvdisasm stride_read.cubin > stride_read.sass

# Alternative extraction from the executable
cuobjdump --dump-sass stride_read > cuobjdump.sass

On the captured Hopper SASS, the key machine instructions include S2R/S2UR for thread/block IDs, IMAD/LEA for index/address generation, LDG.E.CONSTANT for the input load, and STG.E for the output store. The kernel metadata reports a register count of 10.

Detailed Hopper SASS walkthrough

The native sm_90 kernel is small enough to follow from CUDA source to machine instructions. The walkthrough below focuses on architectural meaning rather than manually decoding the 128-bit instruction encodings.

/*0010*/ S2R  R2, SR_TID.X;
/*0020*/ S2UR UR4, SR_CTAID.X;
/*0040*/ LDC  R5, c[0x0][RZ];
/*0050*/ IMAD.WIDE.U32 R2, R5, UR4, R2;

Thread identification. S2R reads the thread ID special register, while S2UR obtains the CTA/block ID as a uniform value. Together with the loaded block dimension, IMAD.WIDE.U32 forms the 64-bit global index corresponding to blockIdx.x * blockDim.x + threadIdx.x. The low/high pieces are carried in the register pair beginning at R2.

/*0060*/ ULDC.64 UR4, c[0x0][0x220];
/*0070*/ ISETP.GE.U32.AND    P0, PT, R2, UR4, PT;
/*0080*/ ISETP.GE.U32.AND.EX P0, PT, R3, UR5, PT, P0;
/*0090*/ @P0 EXIT;

Bounds check. The compiler compares the 64-bit global index against n using low/high pieces. Predicate P0 represents the out-of-range condition; @P0 EXIT implements the early exit. In the initial run, 390625 blocks × 256 threads equals exactly 100,000,000 threads, so there is no partial final block.

/*00a0*/ ULDC UR5, c[0x0][0x228];
/*00c0*/ USHF.R.S32.HI UR4, URZ, 0x1f, UR5;
/*00d0*/ IMAD R7, R3, UR5, RZ;
/*00e0*/ IMAD.WIDE.U32 R4, R2, UR5, RZ;
/*00f0*/ IMAD R7, R2, UR4, R7;
/*0110*/ LEA R6, P0, R4, UR4, 0x2;
/*0120*/ IMAD.IADD R5, R5, 0x1, R7;
/*0130*/ LEA.HI.X R7, R4, UR5, R5, 0x2, P0;

Input address generation. stride remains a runtime kernel argument. The IMAD sequence forms the wide i × stride result. The LEA pair incorporates the input base address and a shift of 2, corresponding to multiplication by sizeof(float) = 4. Conceptually the generated address is in + i × stride × 4.

/*0150*/ LDG.E.CONSTANT R7, desc[UR4][R6.64];

Global load. This is the native Hopper instruction corresponding to the source-level in[i * stride]. Across a warp, the 32 lane-generated addresses presented by this load determine the coalescing/sector behavior studied in this experiment. For stride 1, the working prediction is 32 FP32 lane loads = 128 useful bytes occupying four aligned 32-B sectors.

/*0160*/ LEA R4, P0, R2, UR6, 0x2;
/*0170*/ LEA.HI.X R5, R2, UR7, R3, 0x2, P0;
/*0180*/ STG.E desc[UR4][R4.64], R7;
/*0190*/ EXIT;

Output address and store. Output is always contiguous, so the LEA pair forms out + i × 4, followed by the global STG.E. This matters when interpreting later stride sweeps: input coalescing degrades with stride, while the output-store address pattern remains contiguous.

Multiword arithmetic and the 64-bit bounds comparison

The source uses size_t, so both the global index i and n are 64-bit values. The Hopper SASS performs the bounds check using two 32-bit pieces:

i = [ R3  | R2  ]
      high   low

n = [ UR5 | UR4 ]
      high   low

ISETP.GE.U32.AND    P0, PT, R2, UR4, PT;
ISETP.GE.U32.AND.EX P0, PT, R3, UR5, PT, P0;
@P0 EXIT;

Mathematically, the high word dominates a multiword comparison: if A_hi > B_hi, then A is larger regardless of the low word; if A_hi < B_hi, A is smaller; only when the high words are equal does the low-word comparison decide. The SASS need not implement that rule with branches. The first comparison produces predicate state from the low words and the .EX extended comparison combines it with the high-word comparison to form the final 64-bit result.

Example 1 — high word decides

A = 0x00000002_00000001
B = 0x00000001_FFFFFFFF

A_hi = 2
B_hi = 1

A > B immediately, even though A_lo is much smaller than B_lo.

Example 2 — high words equal, low word decides

A = 0x00000001_00000020
B = 0x00000001_00000010

A_hi == B_hi
therefore compare low words:

0x20 > 0x10  →  A > B

Example 3 — multiword addition analogy

The same idea appears in arithmetic. A 64-bit operation can be constructed from narrower operations by propagating carry/state between words:

A = [A_hi | A_lo]
B = [B_hi | B_lo]

low  = A_lo + B_lo
             |
           carry
             v
high = A_hi + B_hi + carry

result = [high | low]

The extended comparison is conceptually similar: information from one word participates in the operation on the next word, avoiding branch-heavy source-like logic.

Why the high half of i is zero in this run

The experiment launches only 100,000,000 threads, well below 232. Thus the high 32 bits of the current global index are zero. The SASS initializes that high piece with IMAD.MOV.U32 R3, RZ, RZ, RZ. Nevertheless, because the kernel interface uses 64-bit size_t, the generated code remains correct for larger 64-bit index values rather than specializing itself to this particular launch size.

Fatbin: native code and PTX

The executable fatbin contains native sm_90 ELF code as well as an embedded PTX image. The native section is what cuobjdump --dump-sass/nvdisasm expose as Hopper SASS; the PTX section remains a virtual-ISA representation. Keeping these layers separate is important when reasoning about what the hardware actually executes versus what the compiler frontend emitted.

cuobjdump also prints the two 64-bit words encoding each Hopper instruction. For this study we retain those encodings as evidence but analyze the human-readable SASS rather than attempting to decode the bitfields manually.

Why only ~55% DRAM throughput? Scheduler, scoreboard, and occupancy analysis

After validating coalescing, the next question was why a perfectly coalesced streaming copy reached only 55.16% of the profiler's DRAM peak reference. Scheduler and warp-state data show that the kernel is primarily unable to keep enough warps instruction-ready while waiting on memory.

Long-scoreboard dependency

Warp State Statistics report 41.84 warp cycles per issued instruction and approximately 34.7 cycles stalled on a scoreboard dependency associated with an L1TEX operation. NCU attributes this stall class to about 82.9% of the average interval between issued instructions.

The SASS explains the dependency:

LDG.E.CONSTANT R7, ...
        |
        | produces R7
        v
STG.E ..., R7

The store consumes the value returned by the global load. Until the load result is available, the scoreboard marks the dependent operand unavailable and that warp cannot issue the consumer instruction. The 34.7-cycle statistic is a warp-state average; it must not be interpreted as direct HBM latency.

This demonstrates an important GPU performance principle: high or potentially high occupancy does not imply that a kernel successfully hides memory latency. Occupancy describes how much execution state can be resident; eligible-warps and stall metrics describe whether that resident state is actually ready to make forward progress.

Working hypothesis for the 55% result

The evidence now supports a latency-hiding / memory-level-parallelism hypothesis. The kernel has excellent coalescing and abundant grid parallelism, but each thread performs essentially one load whose result feeds the store. Many resident warps simultaneously wait on memory, leaving schedulers without eligible work for 73.35% of cycles. The next controlled experiment will increase independent loads per thread/warp and test whether additional ILP/MLP raises eligible-warps, lowers long-scoreboard stalls, and increases DRAM throughput.
